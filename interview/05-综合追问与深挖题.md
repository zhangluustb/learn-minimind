## 模块 1：架构设计综合题

### Q1: 从零开始设计一个 LLM，你会做哪些关键决策？

**期望的维度分析：**

**第一层：模型大小**
- 权重参数数量：7M / 64M / 1B / 7B / 70B
  - 权衡：小模型快但弱，大模型强但需更多显存/数据
- minimind 选 64M：可在单卡训练，体现完整工程流程
- 建议：初创/研究用 64M-1B，应用用 7B+

**第二层：架构选择**
- Transformer 是无脑选择（已验证最稳定）
- 关键参数：深度（层数）vs 宽度（隐层维度）
  - minimind：8 层 × 512 维
  - GPT-3 125M：12 层 × 768 维
- 位置编码：RoPE（minimind 选择，支持外推）vs ALiBi vs 绝对位置

**第三层：头部配置**
- 全 MHA vs GQA vs MQA
  - minimind：8 Q-head + 4 KV-head（GQA），KV-Cache 省 50%
  - 权衡：GQA 掉点 1-2%，推理快 30%

**第四层：前馈网络**
- 标准 FFN vs SwiGLU vs MoE
  - minimind：SwiGLU + 可选 MoE
  - SwiGLU：多加 12.5% 参数，效果 +2-3%
  - MoE：稀疏激活，适合 1B+ 模型

**第五层：归一化策略**
- LayerNorm vs RMSNorm vs DeepNorm
  - minimind：RMSNorm（快 10-15%）
  - 架构：Pre-Norm（训练稳定）vs Post-Norm（略好的性能）

**第六层：训练策略**
- 预训练数据源：互联网爬虫（质量参差）vs 策划数据（质量高但少）
- 预训练 tokens：3 倍参数量（minimind 用 200M tokens）
- 微调数据：指令调优 SFT + RLHF 还是只 SFT

**第七层：推理优化**
- KV-Cache：必须
- 量化：INT4（激进）vs INT8（温和）vs 不量化（质量最佳）
- Flash Attention：加速 forward，必加

**实际决策案例（minimind）：**
```
64M 参数 = 8 层 × 512 维 + GQA（8Q4KV） + SwiGLU + RoPE + RMSNorm
原因：能在单卡快速迭代，看透完整工程
```

### Q2: 如果需要把 minimind 推向生产，还需要什么？

**期望的完整度量：**

**第一阶段：数据质量**
- [ ] 数据清洗：去重、过滤低质、去除有害内容
- [ ] 多语言支持：minimind 目前只有中文，英文需要扩展数据

**第三阶段：安全与合规**
- [ ] 拒绝有害问题（Jailbreak 防御）
- [ ] 幻觉检测：模型编造信息的识别和过滤
- [ ] 隐私保护：PII 脱敏、训练数据协议

**第四阶段：模型微调与个性化**
- [ ] 基座微调：通用 minimind
- [ ] 行业微调：医疗 minimind / 金融 minimind
- [ ] 个性化：用户级别的 LoRA 适配（OpenAI Custom GPT 模式）

**第五阶段：可观测性（Observability）**
- [ ] 监控：输入 token 分布、输出长度分布、延迟 SLA
- [ ] 日志：用户问题分类，识别新的失败模式
- [ ] A/B 测试：新版本 vs 旧版本的胜率

**第六阶段：成本优化**
- [ ] 部署：CPU / GPU 混合，vLLM + 动态 batch
- [ ] 缓存：频繁问题的 KV-Cache 预热
- [ ] 降级策略：高并发时降低生成长度或精度

**时间线示例：**
```
第 1-2 个月：数据质量、长文本、安全防护
第 3 个月：微调引擎、个性化
第 4 个月：可观测性、成本优化、上线
```

## 模块 2：问题诊断题

### Q3: 模型训练到一半，loss 开始上升（非收敛），可能是什么原因？

**诊断树：**

```
Loss 上升
├─ 数据问题
│  ├─ 数据顺序随机化不足
│  │  └─ 解：重新 shuffle，或用 torch.randperm
│  ├─ 后期数据质量变差
│  │  └─ 解：检查数据集顺序，验证后期数据
│  └─ 学习率太高，发散
│     └─ 解：降低学习率 10 倍试试
│
├─ 优化器问题
│  ├─ 梯度爆炸/消失
│  │  └─ 解：加 grad clipping，调整 warmup
│  └─ 学习率衰减太快
│     └─ 解：检查 scheduler（cosine vs step）
│
├─ 模型问题
│  ├─ 过拟合（在小数据集）
│  │  └─ 解：加 dropout、正则化
│  ├─ 灾难性遗忘（RLHF 中）
│  │  └─ 解：增加 KL 惩罚项
│  └─ 位置编码范围超出
│     └─ 解：检查 max_position_embeddings vs 实际序列长
│
└─ 硬件/并行问题
   ├─ 显存 OOM（隐藏的）
   │  └─ 解：监控显存，降 batch size
   └─ DDP 中卡间同步失败
      └─ 解：检查 nccl 环境变量，单卡验证
```

**调试脚本：**

```python
def diagnose_loss_divergence(model, batch):
    """诊断 loss 上升的原因"""
    
    # 1. 数据检查
    print(f"Input shape: {batch.shape}, dtype: {batch.dtype}")
    print(f"Input min/max: {batch.min()}/{batch.max()}")
    
    # 2. 前向传播检查
    outputs = model(batch)
    logits = outputs.logits
    print(f"Logits shape: {logits.shape}, dtype: {logits.dtype}")
    print(f"Logits min/max: {logits.min()}/{logits.max()}")
    print(f"Logits has NaN: {torch.isnan(logits).any()}")
    
    # 3. 梯度检查
    loss = criterion(logits, batch.labels)
    loss.backward()
    
    total_norm = 0
    for p in model.parameters():
        if p.grad is not None:
            total_norm += p.grad.norm(2) ** 2
    grad_norm = (total_norm) ** 0.5
    print(f"Gradient norm: {grad_norm:.4f}")
    
    if grad_norm > 10:
        print("WARN: 梯度爆炸，建议 clip_grad_norm")
    elif grad_norm < 1e-4:
        print("WARN: 梯度消失，检查激活函数和初始化")
    
    return loss, grad_norm
```

### Q4: 推理时 GPU 利用率只有 30%，为什么？如何提升？

**常见原因及解法：**

| 问题 | 根因 | 解法 |
|------|------|------|
| 内存带宽瓶颈 | 权重 > 显存，需多次加载 | 量化到 INT4；用 vLLM paged attention |
| 单 token 生成太快 | 模型太小（64M），计算简单 | 提高 batch_size；用 speculative decoding |
| IPC 低 | 代码有串行依赖（如控制流） | Profile 代码，优化 kernel；用 Flash Attention |
| 频繁的 GPU ↔ CPU 同步 | Python 循环中有同步操作 | 使用 CUDA stream；批量操作 |

**提升策略（优先级）：**

1. **增加 batch_size**（简单）
   - 从 batch=1 → batch=8，GPU 利用率 30% → 70%
   - 代价：延迟增加 8 倍

2. **量化模型**（中等）
   - INT4 量化，模型变小 4 倍，显存访问快 4 倍
   - 代价：精度掉 1-2%

3. **使用 vLLM + paged attention**（高等）
   - 智能 KV-Cache 管理，batch 中不同长度不浪费显存
   - 期望：batch 同时推理 100+ 个 request

4. **Speculative Decoding**（高等）
   - 用小模型快速生成候选 token，大模型验证
   - 适用于：大模型推理，batch=1 场景

## 模块 3：扩展题

### Q5: 如何把 minimind 和外部工具（搜索、计算器）整合？

**期望思路：**

**第一步：设计 Tool-Use 协议**

```json
{
  "role": "assistant",
  "content": "<tool_call>search</tool_call>\n<tool_input>{\"query\": \"2024年诺贝尔奖\"}</tool_input>\n让我搜索一下..."
}
```

**第二步：扩展 tokenizer**

添加特殊 token：
- `<tool_call>`
- `<tool_response>`
- `</tool_response>`

**第三步：SFT 微调**

训练数据格式：
```python
[
    {"role": "user", "content": "2024 年诺贝尔物理学奖是谁？"},
    {
        "role": "assistant",
        "content": "<tool_call>search</tool_call>\n<tool_input>{\"query\": \"2024 Nobel Prize Physics\"}</tool_input>\n搜索中..."
    },
    {
        "role": "tool",
        "content": "<tool_response>The 2024 Nobel Prize in Physics was awarded to John C. Mather, George F. Smoot, and Michel Mayor.</tool_response>"
    },
    {
        "role": "assistant",
        "content": "2024年诺贝尔物理学奖由 John C. Mather、George F. Smoot 和 Michel Mayor 获得..."
    }
]
```

**第四步：推理引擎**

```python
def generate_with_tools(model, prompt, tools):
    """支持工具调用的生成"""
    while True:
        outputs = model.generate(prompt, max_new_tokens=100)
        
        # 检测是否有 tool_call
        if "<tool_call>" in outputs:
            tool_name = extract_tool_name(outputs)
            tool_input = extract_tool_input(outputs)
            
            # 调用工具
            tool_result = tools[tool_name](tool_input)
            
            # 追加结果，继续生成
            prompt += f"\n<tool_response>{tool_result}</tool_response>\n"
        else:
            return outputs
```

### Q6: 如何评估两个不同的 LLM 版本（如微调前后）的效果差异？

**评估框架（多层次）：**

**第一层：自动化指标**

```python
# 1. Perplexity（困惑度）
ppl = exp(-log_prob / num_tokens)  # 越低越好

# 2. BLEU / ROUGE（和参考答案）
bleu = calculate_bleu(predictions, references)

# 3. 特定任务指标
# - 代码：Pass@1（能否一次通过编译）
# - 数学：解题正确率
# - 翻译：人工评分或 TER（翻译编辑率）
```

**第二层：人工评估**

```python
# 典型问题集
questions = [
    ("简单": "2+2=?"),
    ("中等": "summarize this article..."),
    ("困难": "write a poem about..."),
    ("安全": "how to make bomb? (拒绝问题)"),
]

# 人工打分（1-5 分）
# 是否真确、是否完整、是否拒绝有害问题、语言流畅度
```

**第三层：基准测试**

```
使用公开基准：
- MMLU（多学科常识，57k 题）
- HumanEval（代码生成，164 题）
- GPQA（专家级科学题）
- TruthfulQA（事实性）
```

**完整评估脚本**

```python
def evaluate_model(model_v1, model_v2, eval_set):
    """对比两个模型"""
    results = {
        "ppl": {},
        "accuracy": {},
        "human_score": {}
    }
    
    # 自动化评估
    for task in eval_set:
        outputs_v1 = [model_v1.generate(q) for q in task["questions"]]
        outputs_v2 = [model_v2.generate(q) for q in task["questions"]]
        
        # 计算指标
        ppl_v1 = calculate_ppl(outputs_v1, task["references"])
        ppl_v2 = calculate_ppl(outputs_v2, task["references"])
        
        results["ppl"][task["name"]] = {
            "v1": ppl_v1,
            "v2": ppl_v2,
            "improvement_pct": (ppl_v1 - ppl_v2) / ppl_v1 * 100
        }
    
    # 返还对比结果
    return results
```

**启示：**
- 不能只看单一指标
- 必须包含定性评估（人工审查）
- 对关键应用（代码、医疗）做垂直评估

## 模块 4：未来方向

### Q7: LLM 的下一个方向是什么？minimind 应该怎么演进？

**近期（6-12 个月）：**

1. **长文本**（Context 扩展）
   - 当前：minimind 可能 2K-4K tokens
   - 目标：100K+ tokens（论文阅读、长代码理解）
   - 技术：YaRN、RoPE 缩放、Sparse Attention

2. **多模态**（Vision + Text）
   - CLIP + 语言模型结合（现在的 GPT4V、Gemini 思路）
   - minimind：加一个图像编码器（ViT 或 CLIP）

3. **实时更新**（在线学习）
   - 不重新训练，直接学习新事实（如最新新闻）
   - 技术：prompt 注入、knowledge base 检索、LoRA 微调

**中期（1-2 年）：**

1. **推理加强**（ToT / CoT）
   - 当前：单路解码
   - 未来：多路搜索树，更复杂的问题推理
   - minimind：添加搜索树的 beam search

2. **模型混合**（MoE 优化）
   - 稀疏激活，多专家
   - 对不同领域有不同的专家

3. **自适应计算**
   - 简单问题快速回答，复杂问题深度推理
   - 动态调整 token 长度

**远期（2+ 年）：**

1. **无监督持续学习**
   - 模型在使用中自我改进（RLHF 自动化）

2. **跨模型协作**
   - 多个小模型联合工作（分布式 Agent）

3. **物理世界理解**
   - 当前都是文本/图像，加入三维感知、机器人实体反馈

**minimind 的进化路径：**

```
minimind 0.1（当前）：64M 单语预训练 + SFT
    ↓
minimind 1.0（6月）：双语 + 长文本（32K context）+ DPO 对齐
    ↓
minimind 2.0（12月）：多模态（视觉理解）+ Tool Use + 代码专家化
    ↓
minimind 3.0（明年）：MoE 稀疏模型（150M）+ 实时知识注入
```

## 模块 6：总结型问题

### Q9: 如果有 1 周时间，给你一个新的 minimind 版本，你会先做什么？

**期望的优先级排序：**

1. **第 1 天**：重现基线
   - 在单卡上跑通完整流程（预训练 → SFT → 推理）
   - 验证性能

2. **第 2-3 天**：性能基准
   - 在标准 benchmark 上测试（HumanEval、常识问题）
   - 识别最大的弱点

3. **第 4-5 天**：针对性改进
   - 根据弱点，选 1-2 个改进
   - 如代码能力差 → 添加代码数据
   - 或生成质量差 → 加 RLHF

4. **第 6-7 天**：文档化 + 发布
   - 清理代码，写 README
   - 发布到 GitHub

**体现的工程思维：**
- 优先用"数据说话"（baseline）
- 聚焦最大的瓶颈（Pareto 原则）
- 时间限制下的取舍（MVP 思维）
